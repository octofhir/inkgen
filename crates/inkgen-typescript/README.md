# InkGen TypeScript Backend

A high-performance FHIR TypeScript code generator that transforms canonical FHIR packages into type-safe, idiomatic TypeScript SDKs.

## Features

### Core Generation Capabilities

- **Resource Interfaces**: Generates TypeScript interfaces for all FHIR resources and types
- **Nested Types**: BackboneElement types are extracted and generated as separate, exported interfaces
- **Profile Support**: Generates profile constraint interfaces that extend base resource types
- **Structural Guards**: Optional type guard functions for runtime type validation
- **Multiple Output Modes**: Choose between interface-only, class, or class-with-builder patterns
- **Naming Conventions**: Support for PascalCase, camelCase, and snake_case field naming
- **Deterministic Output**: Uses IndexMap to ensure consistent, sortable code generation

### Code Quality

- **Deterministic Snapshots**: Output is deterministic for reliable testing and diff-friendly reviews
- **TypeScript Compliance**: Generated code follows TypeScript best practices
- **JSDoc Comments**: Includes documentation comments from FHIR resources
- **Proper Imports**: Automatically manages import statements and type references

## Configuration

The TypeScript generator is configured via `inkgen.toml`:

```toml
[languages.typescript]
# Code generation mode
# Options: "interface" (default), "class", "class_with_builder"
mode = "interface"

# Field naming convention
# Options: "pascal" (PascalCase, default), "camel" (camelCase), "snake" (snake_case)
naming_convention = "pascal"

# Output directory structure
# Options: "flat" (all files in one directory), "by_package" (organized by package)
output_structure = "flat"

# Optional: specify output directory (relative to project root)
# output_dir = "src/fhir"

# Features are enabled by default; set to false to opt out.
# structural_guards = false
# generate_profiles = false
# generate_valuesets = false
# profile_classes = false
# zod_schemas = false
```

## Usage

### Via CLI

```bash
# Generate TypeScript code for configured packages (outputs to ./generated by default)
inkgen generate typescript

# Generate with custom output directory
inkgen generate typescript --output ./src/fhir

# Preview without writing files
inkgen generate typescript --dry-run

# Use offline mode (requires packages pre-cached)
inkgen generate typescript --offline
```

### Programmatic Usage

```rust
use inkgen_typescript::{TypescriptGenerator, TypescriptGeneratorConfig, GenerationMode, NamingConvention};
use inkgen_core::BaseStructureService;

let config = TypescriptGeneratorConfig {
    mode: GenerationMode::Interface,
    naming: NamingConvention::PascalCase,
    structural_guards: true,
    output_structure: OutputStructure::Flat,
    output_dir: PathBuf::from("./src/fhir"),
    generate_profiles: true,
    generate_valuesets: true,
};

let generator = TypescriptGenerator::new(config);
generator.generate(&provider, &descriptor, &provider_config).await?;
```

## Architecture

### Generation Pipeline

The TypeScript backend implements the `LanguageGenerator` trait with a two-phase approach:

1. **Phase 1: Analysis & Mapping**
   - Walk all structures in the package
   - Build deterministic name mappings (using IndexMap for consistent ordering)
   - Identify nested types, profiles, and dependencies

2. **Phase 2: Code Generation**
   - Generate structure interfaces with proper field types
   - Extract and generate nested BackboneElement types
   - Generate profile constraint interfaces
   - Emit import statements and index files

### Module Structure

- **lib.rs**: Main generator implementation, template rendering, naming utilities
- **nested.rs**: BackboneElement type extraction and naming
- **profiles.rs**: Profile constraint detection and interface generation
- **valuesets.rs**: Value set code generation (ready for full integration)

## Generated Code Examples

### Resource Interface

```typescript
import type { Address } from "./address";
import type { ContactPoint } from "./contactpoint";

/**
 * Demographics and other administrative information about an individual or animal receiving care or other health-related services.
 */
export interface Patient {
  /** Logical id of this artifact */
  id?: string;
  /** Addresses for the individual */
  address?: Array<Address>;
  /** A contact party (e.g. guardian, partner, friend) for the patient */
  contact?: Array<PatientContact>;
  /** A language which may be used to communicate with the patient about his or her health */
  communication?: Array<PatientCommunication>;
}
```

### Nested Type

```typescript
/**
 * A language which may be used to communicate with the patient about his or her health
 */
export interface PatientCommunication {
  /** The language which can be used to communicate */
  language: CodeableConcept;
  /** Indicates if this is the preferred language */
  preferred?: boolean;
}
```

### Profile Interface

```typescript
/**
 * US Core Patient Profile
 */
export interface USCorePatient extends Patient {
  /** Profile URL for runtime validation */
  readonly __profileUrl: "http://hl7.org/fhir/us/core/StructureDefinition/us-core-patient";
  /** Required by profile (min: 1) */
  identifier: NonNullable<Patient['identifier']>;
}

export function isUSCorePatient(value: Patient): value is USCorePatient {
  return '__profileUrl' in value && value.__profileUrl === 'http://hl7.org/fhir/us/core/StructureDefinition/us-core-patient';
}
```

## Known Issues

### Integration Test Flakiness

The `generates_patient_interface` snapshot test shows intermittent flakiness where the Patient.ts file may not be generated in some test runs, while all dependency types are generated correctly. This appears to be related to async test infrastructure rather than the core generation logic. All other validation tests pass reliably.

**Status**: Documented and being investigated. Does not affect production functionality.

## Performance

- **Deterministic Sorting**: Uses IndexMap throughout for consistent, sortable output
- **Two-Phase Generation**: Separates analysis from code emission for clarity and performance
- **Lazy Evaluation**: Templates are compiled once and reused
- **Streaming Output**: Files are written directly without intermediate representations

## Limitations & Future Work

### Current Limitations

- Value set integration requires loading ValueSet resources (separate infrastructure needed)
- Complex discriminator unions not yet supported
- FHIRPath invariants not validated in generated code
- Extension handling limited to metadata extraction

### Planned Enhancements (TASK-0005)

- Full value set integration with code generation
- Advanced profile helper functions (attach/extract)
- Discriminator union support
- Enhanced extension handling
